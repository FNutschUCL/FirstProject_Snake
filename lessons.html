Lesson 2

Asking well

Some requests work beautifully and some disappoint, and it isn't luck. This lesson is about the difference — and it's the single most transferable thing you'll learn here.

25 min5 tasks1 check
Video: What the assistant actually sees 2 min

The one idea

The assistant can read your project, but it cannot read your mind.

It knows every file you have. It does not know what you pictured, what you'd consider "better", or which of five possible meanings you had in mind.

So the difference between a request that lands and one that disappoints is usually how much context you gave it — not how technical your words were.

Thin make it better It has to guess what "better" means. You'll get something — just probably not what you pictured.
Rich make the game harder — speed it up as the snake grows, and make the food appear further from the snake's head A goal, plus two concrete ways to get there. Almost no room to misread you.

You don't need technical words. "Make it feel like an old arcade machine" is a rich request. "Improve the UI" is a thin one, despite sounding more expert.

The four things worth including

  • The goal — what should be different when it's done
  • Constraints — what must stay the same, or what to avoid
  • An example — "like the pause menu in an arcade game"
  • How you'll judge it — "I should be able to tell at a glance whether I'm winning"

You rarely need all four. Two is usually plenty.

Knowledge check
Which of these gives the assistant the most to work with?

Feel the difference yourself

Ask for the same thing twice — once thin, once rich. Reload between them and compare.

Now write your own rich request

No copying this time. Think of something you want the game to do, and write it out with a goal and at least one constraint. Take thirty seconds over it — that's the whole exercise.

Refining beats restarting

When the result is close but not right, don't start over. Say what to adjust: "that's good, but make the glow subtler". It remembers the conversation, so each round gets closer.

Give it an example to copy

The fastest way to get what you pictured is to point at something that already looks right. You don't need a link — a description of a thing you both know is enough.

Notice how much further that gets you than "make the score look better", with barely more typing.

Say what must not change

The other half of a good request is the guard rail. Without one, the assistant sometimes "improves" things you were happy with.

Lesson 2 complete

You can now steer it deliberately instead of hoping. This is the skill that transfers to every other AI tool you'll ever use.

Lesson 3

What the assistant actually is

Knowing roughly what's going on under the hood explains almost everything the assistant does — the impressive parts and the maddening ones.

18 min3 tasks1 check
Video: Why it sounds certain even when it's wrong 3 min

It predicts what text should come next. It does not look things up, and it does not know things.

That one fact has consequences you'll feel every day:

  • It sounds equally confident when right and when wrong. Confidence is part of the writing style it learned, not a signal about accuracy.
  • It can invent things that look plausible. A function that doesn't exist, a setting that was never there. Normal and expected, not a malfunction.
  • It forgets. Start a new conversation and it knows nothing about the last one — except what it can read in your files.
  • It reads your project. That's why it's useful here. It isn't guessing about your game; it can actually open the file.

None of this makes it unreliable. It makes it a very fast collaborator who is occasionally wrong and never mentions it — which is exactly why the next lesson is about checking.

Knowledge check
The assistant says confidently that it added a feature. The game looks unchanged. Most likely explanation?

Use it as an explainer, not just a builder

Most people only ever ask it to do things. Asking it to explain things is where the learning happens — and it costs nothing.

Worth seeing once so it never surprises you. Start a new conversation in Cline (the + button at the top of its panel), then ask:

Lesson 4

Checking the work

This is the lesson that separates people who use AI from people who work with it. It's also the shortest to describe and the hardest to actually do.

25 min4 tasks1 check

The temptation is obvious: it produced something, it sounded sure, something changed on screen. Accept and move on. Do that often enough and you end up with a project you don't understand and can't fix.

You don't need to read the code. You do need to check the result.

Three habits, in order of value

  • Run it. Every single time. Reload and look. Catches most problems in five seconds.
  • Try to break it. Asked for a pause button? Press it twice. Press it while the snake is dying. Odd cases are where things fall over.
  • Ask it to explain itself. "What exactly did you change and why?" If the explanation doesn't match your request, something drifted.
Knowledge check
You asked for a high score table. It says it's done and a score appears. First thing to do?

Practise it deliberately

Ask for something with obvious ways to fail, then go hunting for them.

Now try to break it: pause twice in a row. Pause during game over. Pause and then press the arrow keys. Anything odd?

If something behaved oddly, tell the assistant exactly what you did and what happened — that's the report that gets it fixed fastest.

Make it account for itself

The hardest check: is it doing the right thing?

Running it catches things that are broken. It doesn't catch things that work perfectly while being wrong.

Now actually verify: eat exactly three pieces. Is the score 30? Not "does a bigger number appear" — is it the right number? Being roughly right is how most subtle bugs survive.

Lesson 5

When it breaks

At some point your game will go blank, freeze, or turn into a different game entirely. This lesson is about having a way back — and about not taking it personally.

15 min3 tasks1 check

Breaking things is not failure. It's most of the job.

It happens to everyone who builds anything, every day. What matters is that you have a way back — and you have three.

  • Say what you see. Not "it's broken" but "the screen went blank after I clicked pause". The assistant can't see your screen, so what you observed is the most useful thing you own.
  • Ask it to undo. "That didn't work, please put it back the way it was." It knows what it just changed.
  • Start fresh. If it's gone in circles three times, a new conversation usually beats a fourth attempt in the old one.

And a safety net worth knowing about: your project keeps its full history. Even a thoroughly broken version can be returned to how it was this morning. Nothing you do here is permanent.

Knowledge check
Which message gets you unstuck fastest?

Break it on purpose

Much better to do this now, deliberately, than by accident later when you care about the result.

The bigger safety net

Sometimes a conversation has drifted so far that undoing step by step isn't worth it. Your project keeps a full history, so you can jump back to a known-good state.

You probably won't need this today. Knowing it exists is what lets you experiment without hesitating.

Lesson 7

What else is this good for?

Snake was a safe place to learn. But the reason this skill matters isn't games — it's the twenty small annoyances in your week that a tiny tool could remove.

45 min4 tasks1 check

Most people never write software because they think software means apps — big things, teams, months. Almost none of the useful stuff is like that.

Most genuinely useful software is small, ugly, and made by one person for one problem.

What people actually build

Real examples, all of which fit in a single afternoon:

  • A tutor made a page that picks a random student name, so she stopped always calling on the same three.
  • A bar manager built a cocktail costing sheet: enter the ingredients, get the pour cost and the margin.
  • Someone learning Spanish made flashcards that show the words she got wrong more often than the ones she knows.
  • A choir organiser built a page that splits people into balanced groups instead of doing it on paper each week.
  • A freelancer made an invoice generator so she stopped editing the same Word file and mistyping the date.
  • A runner built a pace calculator that tells him what splits he needs for a target time.

None of those are impressive to a programmer. All of them saved a real person real time, every week, forever.

Take it home

Genuinely optional. You've finished the course either way, and skipping this costs you nothing at all.

20 minoptional

Everything so far has run in your browser, on GitHub's computers. That was deliberate — it's why you never installed anything. But it has limits: the workspace is eventually cleared away if unused, and you're always one internet connection away from your own work.

If you'd like the same setup on your own machine, permanently, here's the whole thing — written for someone who has never installed a developer tool in their life. Open each part as you get to it.

Step 1 — Install Visual Studio Code

This is the same editor you've been using all course, just running on your own computer instead of GitHub's.

Go to code.visualstudio.com and click the big download button. The site detects your system, so you don't need to choose.

On Windows: run the downloaded .exe. Accept the defaults, but tick "Add to PATH" if you see it — that saves trouble later.

On Mac: open the downloaded .zip, then drag the Visual Studio Code icon into your Applications folder. First time you open it, macOS may ask whether you're sure — say yes.

Open it. A busy screen with a welcome tab appears. That's it for this step.

Step 2 — Install Git

Git is the tool that copies projects between GitHub and your computer, and keeps their history. You'll almost never use it directly, but nothing works without it.

On Windows: download from git-scm.com and run the installer. It asks a lot of questions — accept every default. Really. The defaults are fine and the options are meaningless until you know Git well.

On Mac: open the Terminal app (press Cmd+Space, type "terminal", hit enter) and type:

git --version

If it prints a version number, you already have it. If macOS offers to install developer tools, say yes and wait.

How to check it worked — in a terminal, type:

git --version

You should see something like git version 2.43.0. The number doesn't matter.

Step 3 — Find the terminal inside VS Code

The terminal is the text box where you type commands instead of clicking. It looks intimidating and is genuinely simple: you type a line, press enter, it does the thing.

In VS Code, open it with View → Terminal from the top menu, or the keyboard shortcut Ctrl+` (that's the backtick, usually left of the 1 key). On Mac, Cmd+`.

A panel opens at the bottom with a line ending in $ or %. That's the prompt — it's waiting for you.

Try one harmless command to get the feel of it:

pwd

It prints which folder you're currently in. Nothing more. Every command works like that: type, enter, read the answer.

Step 4 — Copy this project to your computer

"Cloning" just means downloading a project along with its history. Three commands.

First, move to wherever you keep your files. On most systems this puts you in your Documents folder:

cd ~/Documents

Then copy the project down:

git clone https://github.com/FNutschUCL/FirstProject_Snake.git

Then step into the folder it just created:

cd FirstProject_Snake

Now open it in the editor:

code .

That last dot means "this folder" — it isn't a typo. VS Code opens with your project in it.

If code . doesn't work: use File → Open Folder in VS Code instead and pick the folder you just downloaded. Same result.

Step 5 — Install Cline and sign in

In VS Code, click the Extensions icon in the left strip — it looks like four squares with one lifting off. Type Cline in the search box.

Check the publisher says saoudrizwan before installing — there are copycat extensions with similar names.

Click Install. A robot icon appears in the left strip. Click it, and sign in the same way you did in this course — choose Absolutely Free again.

Your assistant is now on your own machine, and it can read the project you just downloaded.

Step 6 — Run the game locally

In the VS Code terminal, from inside the project folder:

python3 serve.py

If that says python3 isn't found, try:

python serve.py

If neither works, you need Python — get it from python.org, and on Windows tick "Add Python to PATH" during install. That tickbox causes more trouble by being missed than anything else in this list.

Once it's running, open a browser and go to:

http://localhost:8080

There's your game, running on your own machine. To stop the server later, click into the terminal and press Ctrl+C.

Starting a brand new project from scratch

Once you're set up, this is how you begin something that isn't a copy of anything.

1. Make a folder for it. In the terminal:

cd ~/Documents
mkdir my-new-project
cd my-new-project

2. Open it in the editor:

code .

3. Open Cline and describe what you want. It will create the files itself — you don't need to make any by hand:

I want to build THING. This folder is empty. Create the files you need, keep it simple, and tell me how to open it when it's ready.

4. To see it, either open the created .html file in your browser directly, or run a small server in that folder:

python3 -m http.server 8080

That's the entire workflow. Folder, editor, describe, look. Everything else is detail.

When something goes wrong

"command not found" — the tool isn't installed, or wasn't added to your PATH. On Windows this usually means reinstalling and ticking the PATH box. Restart the terminal after any install; it only reads PATH when it starts.

"permission denied" — you're trying to write somewhere your user can't. Move the project into Documents rather than a system folder.

"port already in use" — something else is on 8080. Use a different number:

python3 -m http.server 8081

Anything else — copy the error message, paste it to Cline, and add "I don't understand this, what do I do?". Pasting the exact text matters far more than describing it.
